# 视觉 LLM 商场结算单导入设计

## 目标

让现有对账 Demo 能够通过视觉大模型导入扫描版商场结算 PDF，返回可复核的结构化数据，并复用现有的字段映射和对账流程。

第一份验收样本为 `SHAD64结算单-202605.pdf`。

## 本期范围

第一版一次支持导入一份扫描 PDF 或图片文件。暂不将原始文件、LLM 识别结果和字段证据持久化到数据库；暂不生成会计凭证；不替换已存在的 Excel、CSV 和文字版 PDF 导入链路。

## 架构

```text
导入弹窗
  -> POST /api/reconciliation/vision-extractions（multipart 文件上传）
  -> NestJS VisionExtractionService
  -> 将 PDF 页面渲染为 PNG 图片
  -> 调用 OpenAI 兼容的 Chat Completions 接口
  -> 返回结构化候选结果
  -> 用户复核表格、基础信息和字段映射
  -> 进入现有创建对账任务流程
```

视觉模型服务只在后端通过环境变量配置：

```text
VISION_LLM_BASE_URL
VISION_LLM_API_KEY
VISION_LLM_MODEL=gpt-5.4
```

适配器调用 OpenAI 兼容的 `POST /chat/completions` 接口，将渲染后的页面图片作为 Data URL 发送给模型。浏览器端不会接触 API Key。

## 识别结果约定

服务端返回 `VisionExtractionResult`，包含：

- `sourceType: vision_llm`：明确标记数据来自视觉 LLM。
- 已归一化的 `headers` 和 `rows`：可直接供现有表格处理和字段映射逻辑使用。
- 推断出的账单基础信息：商场、门店、门店编码、账期起止和账单类型。
- 各业务字段的证据：数值、原始文字、页码和置信度。
- 警告信息：字段缺失、低置信度和金额勾稽不一致。

模型提示词要求只返回在原始单据上可见的数据。如果某个值看不清或不存在，必须返回 `null`，不得自行推断或计算缺失金额。

## 数据校验

服务端在返回结果前执行以下校验：

- 在调用模型前校验文件类型和最大文件大小。
- 只接受允许的字段名、金额格式和日期格式。
- 金额使用现有金额清洗规则统一解析。
- 当销售额、退款、扣点、活动费和实结金额同时可见时，校验结算金额是否勾稽。
- 勾稽不一致只生成警告，不会用公式结果覆盖模型识别出的原始金额。

前端仍要求用户确认基础信息和字段映射，之后才允许创建对账任务。现有 ERP 账期过滤和对账规则不变。

## 界面交互

当上传的 PDF 没有文字层时，导入弹窗提供“使用视觉识别”操作，而不是直接显示当前的 PDF 解析失败提示。

识别过程中，账单上传区域展示处理中状态。识别成功后，页面展示自动识别的基础信息、警告和原有的字段映射步骤。识别失败时，显示可操作的错误信息，同时保留用户已上传的 ERP 文件。

## 异常处理

- 未配置模型服务：返回明确提示，说明缺少哪些环境变量。
- 模型服务返回不支持的响应：返回通用识别失败信息；日志只记录 HTTP 状态，不记录密钥或单据图片内容。
- 模型返回格式错误的 JSON：拒绝本次结果，提示用户重试或使用手工 Excel 导入。
- 低置信度或金额勾稽失败：仍返回候选数据和警告，但要求人工复核。

## 测试

单元测试覆盖：

1. 模型请求体使用视觉图片输入，并要求 JSON 格式输出。
2. 合法模型 JSON 能转换为预期的标准化识别结果。
3. 未识别出的金额保持缺失，不会被系统伪造为金额。
4. 结算金额勾稽不一致时会生成警告。
5. 模型返回格式错误时会被拒绝。

完成后需要执行服务端重点测试、前端类型检查，并使用 `SHAD64结算单-202605.pdf` 做人工验收。

## 暂不包含

- 第二模型复核或多模型共识。
- 从人工修正中自动学习模板。
- 原始文件和字段证据的永久存储。
- 面向生产规模的多页明细行提取。
- 传统 OCR 引擎集成。

这些内容将在本案例跑通后，作为后续独立迭代推进。
