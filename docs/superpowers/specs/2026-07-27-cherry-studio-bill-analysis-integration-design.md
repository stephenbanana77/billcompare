# Cherry Studio 账单分析集成设计

## 1. 目标

将商场对账系统作为店员的正式业务工作台，将 Cherry Studio 作为已确认账单的只读分析入口。两种入口共享同一数据库、权限体系、指标口径和分析服务。

第一版支持以下工作方式：

- 店员在对账系统上传结算单，完成 OCR、LLM 字段映射、人工复核和确认。
- 对账系统将确认后的账单主信息、标准字段、销售明细和费用明细写入后端数据库。
- 用户可以在对账系统内使用分析助手，也可以在 Cherry Studio 中提问。
- Cherry Studio 通过 MCP 工具查询后端计算的结构化结果，不直接连接数据库或读取未确认的模型结果。
- 店员仅查看本门店，区域经理查看本区域，财务和管理员查看全部授权数据。

## 2. 非目标

第一版不包含：

- Cherry Studio 直接修改、确认或删除账单。
- 将原始 PDF、OCR 全文或未复核 LLM 结果批量写入 Cherry Studio 知识库。
- 自动生成会计凭证或直接写入 ERP。
- 预测销售额、现金流或其他需要独立预测模型的功能。
- 固化甲方最终组织结构；第一版权限规则可配置，后续可调整。

## 3. 方案选择

### 3.1 推荐方案：MCP 工具服务

在现有 NestJS 后端中增加独立的账单分析服务和 MCP 接入层。Cherry Studio 将该 MCP 服务配置为企业工具，模型根据用户问题调用工具，并使用工具返回的结构化数据生成分析结论。

选择 MCP 的原因：

- 与 Cherry Studio 的工具调用体验一致。
- 工具参数、返回结构和用途可以明确描述。
- 权限、统计口径和审计均由业务后端控制。
- 当前系统内的分析助手可复用同一分析服务，不产生两套统计逻辑。

### 3.2 未采用方案

- 单纯 REST/OpenAPI：可以保留为当前前端接口，但不作为 Cherry Studio 的主要连接方式。
- 定期导入知识库：仅适合合同、制度和字段说明，不适合频繁变化的金额统计和细粒度门店权限。

## 4. 总体架构

```text
店员/经理/财务
  |-- 商场对账系统
  |     上传 -> OCR+LLM -> 字段映射 -> 人工复核 -> 确认
  |     分析助手 -> 统一分析服务
  |
  `-- Cherry Studio
        自然语言问题 -> MCP 工具 -> 统一分析服务

业务后端
  |-- 账单持久化服务
  |-- 统一分析服务
  |-- REST API（供当前系统）
  |-- MCP Server（供 Cherry Studio）
  |-- 权限服务
  `-- 审计服务

PostgreSQL
  |-- 已确认账单及明细
  |-- 门店、区域、用户、角色
  `-- 操作和查询审计记录
```

## 5. 系统职责

### 5.1 商场对账系统

- 接收 PDF 并执行 OCR 和视觉 LLM 识别。
- 展示字段映射、来源证据、销售明细和费用明细。
- 允许店员修正识别结果并进行人工确认。
- 将确认结果持久化，并保留确认人、确认时间和修改记录。
- 提供业务工作台和内置分析助手。

### 5.2 统一分析服务

- 从数据库查询已确认账单。
- 计算销售额、发票金额、扣款金额、实付金额及费用分类统计。
- 计算环比、占比、门店对比和异常指标。
- 为 REST 和 MCP 返回相同的数据结构和指标口径。
- 不依赖大模型完成金额计算。

### 5.3 Cherry Studio

- 理解用户自然语言意图并选择 MCP 工具。
- 根据工具返回的结构化结果生成解释、摘要和报告。
- 不负责权限判断、金额汇总或正式账单状态管理。

## 6. 数据模型

### 6.1 已确认账单

`confirmed_settlement_bills` 至少包含：

- `id`
- `source_file_name`
- `mall_id`
- `store_id`
- `period_start`
- `period_end`
- `settlement_no`
- `sales_amount`
- `invoice_amount`
- `deduction_total`
- `settlement_amount`
- `recognition_payload`：确认时的完整结构化识别结果
- `status`：`confirmed`、`superseded`、`revoked`
- `confirmed_by`
- `confirmed_at`
- `created_at`
- `updated_at`

### 6.2 明细数据

销售明细和费用明细分别存储，避免仅依赖 JSON 查询：

- `settlement_sales_lines`
- `settlement_fee_lines`

明细表保留账单 ID、顺序、行类型、业务字段、来源页码和复核后的值。原始结构化 JSON 同时保留，用于审计和后续字段扩展。

### 6.3 组织与权限

- `organizations`
- `regions`
- `malls`
- `stores`
- `users`
- `user_data_scopes`

`user_data_scopes` 表达用户可访问的门店、区域或全部数据范围。角色决定可执行操作，数据范围决定可查询记录，两者分开管理。

### 6.4 审计

记录以下事件：

- 账单确认、修改、撤销和替代。
- REST 和 MCP 分析查询。
- 查询用户、工具名、时间范围、数据范围、请求 ID、结果行数和执行时间。

审计日志不保存模型生成的完整自然语言回答，避免重复保存敏感经营数据；必要时可保存回答哈希和会话引用。

## 7. 确认流程

当前识别页仅将复核结果保存到浏览器 `localStorage`。第一阶段必须替换为后端持久化流程：

1. 店员上传并识别账单。
2. 前端保留识别中的临时状态。
3. 店员修正字段并点击确认。
4. 后端校验门店、账期、核心金额和明细结构。
5. 后端在单个事务中写入账单、明细和审计记录。
6. 后端返回不可变的确认版本 ID。
7. Cherry Studio 和内置分析助手仅查询 `confirmed` 版本。

相同门店和账期重复确认时不直接覆盖旧数据。系统创建新版本，将旧版本标记为 `superseded`，保证历史可追溯。

## 8. MCP 工具设计

第一版提供只读工具：

### `list_settlement_bills`

按门店、区域、商场、账期和状态查询账单列表。普通用户不能通过参数扩大自身数据范围。

### `get_settlement_bill`

返回指定账单的核心字段、销售明细、费用明细、确认信息和来源引用。

### `summarize_store_period`

返回指定范围内的销售额、发票金额、扣款金额、实付金额、账单数量和缺失账期。

### `compare_periods`

比较两个时间范围，返回绝对变化、变化率和参与计算的账单数量。

### `analyze_fee_changes`

按费用名称或代码汇总金额、占比和期间变化，返回增长明显的费用项。

### `find_abnormal_bills`

根据确定性规则查找金额勾稽异常、重复账期、缺失账期、费用突变和未识别关键字段。

### `compare_stores`

为有多门店权限的用户比较门店销售、扣款率和实付金额。店员角色调用时只返回本人门店。

### `export_analysis`

导出当前授权范围内的结构化分析结果。第一版支持 JSON 和 CSV，文件设置有效期并记录审计日志。

## 9. 权限与身份认证

第一版角色和数据范围：

| 角色 | 默认数据范围 | 当前系统 | Cherry Studio |
| --- | --- | --- | --- |
| 店员 | 本门店 | 录入、复核、确认 | 只读分析 |
| 区域经理 | 本区域门店 | 查看与复核 | 只读分析与门店比较 |
| 财务 | 全部授权门店 | 复核与管理 | 全局只读分析 |
| 管理员 | 全部数据 | 系统与权限管理 | 全局只读分析 |

MCP 请求必须携带可验证的用户身份。服务端根据用户身份加载数据范围，并在每个查询中附加范围过滤。模型提示词、工具参数和前端传入的门店 ID 都不能替代服务端授权。

企业环境优先采用 OAuth/OIDC 或 Cherry Studio 可传递的企业身份令牌。开发演示阶段可使用短期签名令牌，但每个令牌仍绑定具体用户和角色，禁止共享全局管理员密钥。

## 10. 数据流示例

用户在 Cherry Studio 中提问：

> 阿迪达斯 086203 门店最近三个月销售和扣款有什么变化？

处理流程：

1. Cherry Studio 识别门店、时间范围和分析意图。
2. 调用 `summarize_store_period` 获取期间汇总。
3. 调用 `analyze_fee_changes` 获取费用变化。
4. MCP 服务验证用户是否有权访问 086203 门店。
5. 分析服务只读取已确认账单并完成数值计算。
6. Cherry Studio 根据结构化结果生成自然语言说明，并标注账期、账单数量和数据更新时间。

## 11. 错误处理

- 无权限：返回明确的授权错误，不暴露目标门店是否存在。
- 无数据：返回空结果、授权范围和实际查询区间，不让模型自行补数。
- 账期缺失：返回缺失月份列表，并要求回答中标明数据不完整。
- 重复或替代版本：只统计当前有效的 `confirmed` 版本。
- MCP 或模型暂时不可用：不影响店员在业务系统中的上传、复核和确认工作。
- 分析超时：返回请求 ID，记录工具、参数摘要和执行阶段，便于排查。

## 12. 安全要求

- Cherry Studio 不获得数据库账号。
- MCP 工具默认不返回原始 PDF、完整 OCR 文本或其他门店的数据。
- 金额统计使用数据库数值字段，不让 LLM 自行计算。
- 导出链接短期有效，且受用户身份约束。
- API 密钥和模型密钥仅保存在服务端环境变量中。
- 所有工具限制最大时间范围、返回行数和导出大小。

## 13. 测试与验收

### 13.1 功能验收

- 确认账单后刷新或更换电脑，数据仍可查询。
- 店员能在当前系统和 Cherry Studio 获得相同的本店期间汇总。
- 区域经理能比较授权区域门店。
- 财务能查询全部授权数据。
- 未确认账单不会出现在任何分析结果中。

### 13.2 权限验收

- 店员构造其他门店 ID 仍无法查询。
- Cherry Studio 提示模型查询越权门店时，MCP 服务拒绝请求。
- 导出接口不能绕过数据范围。
- 被撤销权限的用户无法继续使用旧令牌查询。

### 13.3 数据验收

- 分析汇总与数据库账单逐项核对一致。
- 销售额、扣款金额和实付金额的期间汇总精确到分。
- 费用分类汇总等于参与统计的费用明细之和。
- 同账期替代版本不会重复计入。

## 14. 第一阶段交付范围

第一阶段按以下顺序交付：

1. 已确认账单、销售明细、费用明细和版本审计的数据库结构。
2. 识别页确认操作改为后端事务持久化。
3. 门店、区域、用户角色和数据范围的基础模型。
4. 统一分析服务及对应 REST API。
5. 第一版只读 MCP Server 和八个分析工具。
6. Cherry Studio 企业工具配置与身份传递。
7. 当前系统内复用同一分析服务的对话入口。
8. 权限、统计口径、异常处理和端到端验收测试。

## 15. 成功标准

- 店员只在对账系统完成日常账单工作，不需要在 Cherry Studio 重复上传文件。
- Cherry Studio 可以基于已确认数据回答期间汇总、费用变化和门店比较问题。
- 两个入口对相同问题使用同一统计服务，核心金额完全一致。
- 任何用户都不能通过自然语言、工具参数或导出功能越过其数据范围。
- Cherry Studio 不可用时，账单识别、复核和确认流程仍可独立运行。
